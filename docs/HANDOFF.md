## tradingview — 평행채널 지표 신설 (2026-09-09, 미커밋)

`tradingview/indicator/[IND-03] 평행채널.pine` 신설(614줄). `[STR-02] 거래량 스파이크 스위칭` 의
진입 필터로 쓸 값 두 개를 내는 것이 목적 — **위치 %**(채널 안 어디에 있나. 0 하단·100 상단,
0 미만·100 초과는 이탈)와 **폭 %**. 아직 전략에 이식하지 않았고 지표 단독이다.
`strategy/[STR] 거래량 역추세.pine` 은 사용자가 세션 전에 삭제했다.

### 확정된 구조 (뒤집으려면 재협의)
- 슬롯 = 주기 하나. 슬롯마다 **고점선·저점선 두 채널**을 함께 낸다. 급등에서는 이상치가 저점
  쪽에, 급락에서는 고점 쪽에 생겨 **한 기준으로 통일하면 어떤 주기가 반드시 망가진다**(실측).
  기준을 자동 전환하는 안은 **이탈을 화면에서 지워버려** 기각.
- 세대를 둘(현재·직전) 그린다. 채널이 갈리는 순간이 대개 이탈이 일어난 순간이라, 현재 세대만
  두면 뚫고 나간 그림이 사라진다.
- 폭은 두 꼭지 사이(닫힌 구간)에서만 잰다. 구간 밖을 포함하면 이탈이 "채널이 넓어진 것"으로
  흡수된다.
- 색=주기 / 선 모양=고점 실선·저점 파선 / 투명도=세대 / 회색=유효 범위 밖.
- 확정 표식(삼각형)은 그 채널을 **알 수 있게 된 시각**. 그 왼쪽은 나중에 돌아본 구간이다.

### 막힌 길 (다시 시도하지 말 것)
1. **봉 수 조절** — 실측. 1D 저점선에서 좌우 5면 급등 이전에 눌러앉고(위치 400), 3이면 급등
   구간 안의 두 저점을 이어 기울기가 폭발한다. 어느 값이든 한쪽으로 망가진다.
2. **구간 최저 + 폭 최소** — Codex 가 수학으로 증명. 관통 0 조건에서 L1 이 공통이면
   `W_오래된 >= W_가까운` 이라 **오래된 후보의 폭이 가까운 후보보다 작아질 수 없다.** 그래서
   "K개를 뒤로 훑는다"가 사실상 최근접 후보만 고르는 것과 같다. 고점선의 급강하 채널을
   목적함수로 완만하게 만드는 것도 불가능(오래된 적격 후보는 기울기가 더 음수).
   코드에 `앵커 방식 = 구간 최저` 로 남아 있으나 **실험용이고 기본이 아니다.**
3. **관통 검사로 좋은 채널 가려내기** — 실측. 못 쓰는 채널(1D 저, 위치 394)의 관통이 0이고
   쓸 만한 채널(1D 고, 위치 -19)의 관통이 22.7% 로 **반대로 나왔다.** 관통은 "선이 봉을
   뚫는가"만 재고 "채널이 지금 쓸모 있는가"는 못 잰다.

셋 다 "채널 하나를 잘 만든다"는 접근이었다. 그래서 **여러 채널을 만들어 두고 쓸 만한 것만
고르는 쪽**으로 방향을 바꿨다 — 유효 위치 여유 M(기본 50 → 유효 범위 -50~150), 벗어나면 회색.

### 확인된 것
- 사용자의 판단 기준은 "내가 그린 것과 같은가"가 아니라 **"그려진 것이 납득이 가는가"** 다.
  피봇 방식이 그 기준을 더 만족했다고 사용자가 확인 → 기본을 피봇으로 되돌렸다.
- 수동 채널(사람이 두 점 클릭)은 삭제했다. `confirm=true` 라 지표를 다시 추가할 때마다 클릭을
  요구해 불편했고, 판단 기준이 바뀌며 정답지 역할이 줄었다.
- Codex xhigh 검수 3회. 확정 결함 넷 중 셋(구간 자료 완전성 / 부적격인데 선·값이 남음 /
  같은 앵커 시각의 값 변경 미저장)과 상위 주기 확정 문제까지 고쳤다.

### 남은 것
1. **정확한 앵커 복원** — 앵커 시각이 상위 봉의 시작이라 어긋난다(지금은 봉 중간으로 반 칸
   보정해 최대 오차를 절반으로 줄인 상태. 1D 슬롯·1시간 차트에서 기울기 최대 약 10%).
   없애려면 상위 봉 안의 실제 극값 시각을 차트 봉에서 복원해야 하고, 기울기·폭을 다시 재야
   하므로 **계산을 차트 쪽으로 옮기는 재작성**이 된다. **전략 이식 전에는 필요하다** —
   위치 % 가 곧 진입 판정이 되므로.
2. **M = 50 의 근거** — 회색(범위 밖) 채널 중에 쓸 만한 게 있는지 며칠 보고 정한다.
3. **세대 안정성 정책** — 피봇 방식에서는 교체가 드물어 당장 급하지 않다.
4. **전략 이식** — `[STR-02] 거래량 스파이크 스위칭` 에 같은 로직을 복제한다(Pine 에 파일 간
   import 가 없다). 이식 시 `상위 주기 확정 대기` 를 반드시 켜야 백테스트가 실시간을 재현한다.

**마지막 상태:** 컴파일 에러 1건(옛 반환 튜플 잔여 2줄)을 고쳤고 **사용자 재확인 전이다.**

## 바이낸스 마틴게일 분할주문 크롬 확장 (2026-09-07 신설, 미커밋)

`extension/` 폴더 신설. 지정가 기준으로 **가격은 등비**, **금액은 마틴게일(등비)** 로 나눠
지정가 주문을 한 번에 걸어 두는 크롬 확장(MV3). 바이낸스 기본 scale order 는 금액을 균등
또는 직선 증감으로만 나눠서 이 배분이 안 되는 것이 만든 이유다. 상세는 `extension/README.md`.

**서버(`springboot/`)를 한 줄도 안 건드린다.** 서버 autotrade 에 LIMIT 주문 타입을 추가하는
안도 검토했으나, 그 폴더를 Codex 세션이 작업 중이라 충돌을 피해 독립 확장으로 갔다.
Jenkinsfile 의 변경 감지가 `springboot/`·`frontend/`·`nexus/` 세 접두사만 보므로
`extension/` 은 배포 파이프라인에 안 걸린다(확인함).

### 확정된 설계 (사용자와 합의, 뒤집으려면 재협의)
- 크롬 확장 MV3, 스토어 미등록 언팩드 로컬 설치, **외부 라이브러리 0개**.
- 바이낸스 REST 직접 호출. 화면 자동조작(DOM 클릭)과 세션 쿠키 방식은 기각
  (전자는 중간에 조용히 어긋나고 예행연습 불가, 후자는 로그인 세션이 API 키보다 권한이 큼).
- **본계정** API 키. 권한은 Reading + Futures 만, 출금·이체·현물·옵션 전부 끔.
  서브계정은 바이낸스 화면 전환이 안 돼 "보는 계좌와 주문 나가는 계좌가 다른" 상태가 되어 기각.
- 키는 `chrome.storage.local`. **처음엔 `session` 이었는데 확장을 새로고침할 때마다 지워져
  못 쓴다는 것이 실사용에서 드러나 바꿨다**(2026-09-07). 위험은 키 권한 축소와 IP
  화이트리스트로 닫는다.
- 포지션 모드는 **양방향(Hedge)** 기준. `positionSide` 를 LONG/SHORT 로 명시한다.
- 제외 회차가 생겨도 **건너뛰고 진행**(전체 거부 아님). 전송 실패는 확정 거부와 접수 불명을
  나눠 거부는 계속, 불명은 즉시 중단.
- 배율은 0.1 단위 스테퍼 1.0~3.0, 기본 2.0. 텍스트 입력 없음.

### 계산의 핵심 (되돌리면 안 되는 것)
- **부동소수를 쓰지 않는다.** `Math.floor(a / step)` 은 경계에서 한 단위 틀리고
  (`0.1*3 === 0.30000000000000004`) 그 수량은 LOT_SIZE 로 거부된다. 양자화는 전부 BigInt.
- **목표 금액과 실제 금액을 분리해 표시한다.** 수량을 주문단위로 내리면 실제 금액은 목표보다
  작고, 최소수량·최소명목에 걸리는 앞 회차는 아예 안 나간다. 배율이 클수록 앞 회차가 작아져
  이런 제외가 생기는 것이 정상이다.
- **PERCENT_PRICE 는 방향마다 한쪽만 막는다.** 매수는 위쪽만(`price <= mark * multiplierUp`),
  매도는 아래쪽만. 양쪽을 다 검사하면 분할 매수가 통째로 막힌다 —
  실제로 그 버그를 냈다가 화면에서 발견해 고쳤다(2026-09-07, `test/filters.test.mjs` 가 고정).
- **증거금 비교 대상은 가용 잔고다.** `필요 증거금 = 실제 명목금액 / 레버리지` 를
  `availableBalance` 와 비교한다. 지갑 잔고를 쓰면 이미 걸어 둔 주문·포지션이 잡아 둔
  증거금을 이중으로 세게 된다. 레버리지나 잔고를 못 읽었으면 `UNKNOWN` 으로 두고 막지 않는다 —
  검사 못 한 것과 부족한 것은 다르다.
