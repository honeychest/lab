# 바이낸스 마틴게일 분할주문 (크롬 확장)

기준가에서 일정 범위까지, **가격은 등비**로 나누고 **금액은 마틴게일(등비)**로 배분해
지정가 주문을 한 번에 걸어 둔다. 바이낸스 기본 scale order 는 금액을 균등 또는 직선
증감으로만 나눠서 이 배분이 안 된다 — 그게 이걸 만든 이유다.

서버(`springboot/`)와는 무관하게 돈다. Jenkins 변경 감지가 `springboot/` · `frontend/` ·
`nexus/` 세 접두사만 보므로 이 폴더는 배포 파이프라인에 걸리지 않는다.

## 구조

```text
extension/
  src/
    core/
      chase.js                    Chase 수정 여부와 확인 결과를 판단한다
      decimal.js                  부동소수 없이 가격·수량을 계산한다
      expected-pnl-validation.js  예상 손익 요청의 입력 형식을 검증한다
      filters.js                  바이낸스 심볼 필터와 주문 가능 여부를 판단한다
      margin.js                   필요한 증거금과 가용 잔고를 비교한다
      mutex.js                    백그라운드 작업의 전역 단일 잠금을 판단한다
      plan.js                     분할 주문의 가격·금액·수량 계획을 계산한다
      watch.js                    조건 감시의 상태 전이와 발동 조건을 판단한다
    background/
      binance.js                  바이낸스 REST 요청과 응답 파싱을 담당한다
      execution.js                주문 전송·재조회·실패 격리를 담당한다
      index.js                    service worker 메시지와 작업 흐름을 연결한다
      keys.js                     API 키를 storage에서 읽고 저장한다
      signer.js                   바이낸스 서명 문자열을 만든다
      stream.js                   시장(가격)·공개(호가)·계정(주문 이벤트) 웹소켓 3개 연결과 재연결·listenKey를 담당한다
      watch.js                    조건 감시의 백그라운드 실행과 알림을 담당한다
    content/
      index.js                    패널 UI와 호가 클릭을 담당한다
      orders-bridge.js             바이낸스 미체결 표의 React 주문 속성을 읽는다
      panel.css                    패널의 화면 스타일을 담당한다
    options/
      options.html                 API 키 설정 화면을 제공한다
      options.js                   API 키 설정을 저장·검증한다
  test/                            core·background의 계산·파싱·상태 전이를 검증한다
  icons/                            확장 프로그램 아이콘을 둔다
```

바이낸스 주문 번호는 자바스크립트 숫자 범위를 넘을 수 있으므로 응답의 주문 식별자는
문자열로 다룬다. 반면 거래 번호처럼 이 확장이 식별자로 사용하지 않는 정수 키는 숫자로
남긴다. 바이낸스 DOM을 읽는 곳은 두 곳이다. `src/content/index.js`는 호가를 클릭해
기준가를 채우고, `src/content/orders-bridge.js`와 `src/content/index.js`는 미체결 표의
주문 속성을 읽어 예상 손익을 표시한다. 이 DOM 값은 표시와 기준가 입력에만 쓰며 주문
전송·Chase·조건 감시의 상태 판단에는 쓰지 않는다.

## 설치

1. 크롬에서 `chrome://extensions` 를 연다
2. 우측 상단 **개발자 모드**를 켠다
3. **압축해제된 확장 프로그램을 로드** 를 눌러 이 `extension/` 폴더를 지정한다
4. 확장 세부정보 → **확장 프로그램 옵션** 에서 API 키를 넣는다
5. `https://www.binance.com/ko/futures/BTCUSDT` 같은 선물 화면을 열면 우측에 패널이 뜬다

거래 전용 크롬 프로필을 따로 만들고 거기에만 설치하는 것을 권한다. 확장은 프로필 단위로
격리되므로, 다른 프로필의 확장이 이 프로필의 쿠키나 페이지에 닿지 못한다.

## 패널 위치

접으면 폭이 내용에 맞게 줄고, **접힌 상태에서만** 머리 부분을 끌어 옮길 수 있다. 펼친 채로
끌리면 값을 만지다가 창이 따라 움직인다. 옮긴 자리와 접힘 여부는 기억해 뒀다가 다음에 열 때
그대로 쓴다. 펼쳤을 때 화면 아래로 밀려나면 보이는 데까지 자동으로 끌어올린다.

## 호가 클릭으로 기준가 채우기

페이지의 오더북에서 가격을 클릭하면 기준가로 들어온다. 패널의 `호가클릭` 버튼으로 끌 수 있다.

이것이 **바이낸스 DOM 을 읽는 첫 번째 곳**이다. 마크업이 바뀌면 못 읽게 되는데, 그때는
"아무 일도 안 일어남" 이 되어야지 엉뚱한 값이 들어가면 안 된다. 그래서 두 겹으로 거른다.

- `45.46K` · `1.30M` 처럼 접미사가 붙은 값은 수량이라 후보에서 뺀다
- 읽은 값이 현재 호가의 ±50% 밖이면 버린다 (수량·누적합·다른 심볼 가격이 여기서 걸린다)

두 번째 예외는 미체결 주문 표의 예상 손익 표시다. 페이지 세계 보조 스크립트가 표의 React
주문 속성을 읽어 표시 전용 `data-chs-*` 속성으로 전달하고, 격리된 content script가 청산 주문의
가격 칸에 예상 손익을 붙인다. 예상 손익은
`(주문 가격 - 진입가) × 주문 남은 수량 × (LONG이면 1, SHORT이면 -1)`로 계산하며 수수료와
펀딩은 제외한다. 표 구조나 가격 검증이 맞지 않으면 잘못된 줄에 붙이지 않고 표시하지 않는다.
이 속성은 표시 전용이며 Chase·조건 감시·주문 동작에서는 읽지 않는다.

깨지면 기준가를 직접 입력하면 된다. 그래도 불편하면 패널 안에 자체 호가창을 그리는 쪽으로
바꿀 수 있다 — 그건 DOM 에 의존하지 않는다.

## API 키 권한

이 확장이 쓰는 권한은 선물 거래 하나뿐이다.

| 항목 | 설정 |
|---|---|
| Enable Reading | 켬 (고정) |
| Enable Futures | 켬 |
| Enable Withdrawals | **끔** |
| Enable Spot & Margin & Stock Trading | **끔** |
| Enable European Options | **끔** |
| Permits Universal Transfer | **끔** |
| IP access restrictions | 신뢰 IP 만 |
| Symbol Whitelist | 거래할 심볼만 등록 (권장) |

이체 권한을 끄면 이 키로는 **선물 지갑 잔고만** 건드릴 수 있다. 현물 지갑은 못 만지고
현물에서 선물로 끌어올 수도 없으므로, 선물 지갑에 운용액만 두면 최악의 경우가 그 금액으로
닫힌다.

키는 `chrome.storage.local` 에 둔다. 처음에는 `session`(메모리 전용)으로 뒀는데 **확장을
새로고침할 때마다 지워져서** 쓸 수가 없었다. `local` 은 디스크에 평문으로 남는 대신 한 번
넣으면 유지된다.

그 대신 키 자체의 권한으로 위험을 닫는다. 위 표대로 두면 키가 유출돼도 **신뢰 IP 밖에서는
아무것도 못 하고**, 안에서도 지정 심볼을 선물 지갑 잔고로 거래하는 것까지다. 돈을 빼갈 수는 없다.

`session` 이 실제로 더 막아 주는 것은 **파일을 읽는 공격**(훔친 노트북, 프로필 폴더 동기화,
파일만 읽고 나가는 스크립트)이다. 메모리를 읽거나 키 입력을 가로채는 수준의 침해라면 `session`
으로도 못 막는다 — 키를 입력하는 순간 메모리에 있기 때문이다.

확장끼리는 저장소가 격리되므로 다른 확장은 이 값을 읽지 못한다. content script 에는 절대
넘기지 않는다 — 읽는 곳은 `keys.js` 와 `binance.js` 뿐이다.

이상하다 싶으면 바이낸스에서 그 키를 삭제하는 것이 가장 확실한 복구다.

## 계산

```
가격  롱 q = (1 - 범위)^(1/(회차-1)) ,  숏 q = (1 + 범위)^(1/(회차-1))
      p(i) = 기준가 * q^(i-1)
      호가단위 반올림은 유리한 쪽 — 롱 매수는 내림, 숏 매도는 올림

금액  배율 r != 1 : a(1) = 총액 * (r-1) / (r^n - 1),  a(i) = a(1) * r^(i-1)
      배율 r == 1 : a(i) = 총액 / n   (균등 분할. 마틴게일이 아니다)

수량  floor(목표금액 / 가격 / 주문단위) * 주문단위
```

**목표 금액과 실제 금액을 나눠서 보여준다.** 수량을 주문단위로 내리면 실제 금액은 목표보다
작아지고, 최소수량·최소명목에 걸리는 회차는 아예 안 나간다. 배율이 클수록 앞 회차가 작아져서
이런 제외가 생기는 것이 정상이다. 표에 사유가 그대로 표시되므로 회차를 줄이거나 총액을 늘려
조정하면 된다.

예: BTCUSDT, 기준가 80,000, 범위 40%, 9회, 총액 30,000, 배율 2.0

| 회차 | 가격 | 목표 | 수량 | 실제 | 비고 |
|---|---|---|---|---|---|
| 1 | 80,000.0 | 58.7 | 0.000 | - | 최소수량 미달 |
| 2 | 75,051.4 | 117.4 | 0.001 | - | 최소명목 미달 |
| 3 | 70,408.9 | 234.8 | 0.003 | 211.2 | |
| ... | | | | | |
| 9 | 48,000.0 | 15,029.4 | 0.313 | 15,024.0 | |

목표 30,000 / 실제 29,666.1 / 평균단가 50,798.1 / 전송 7건 제외 2건

## 안전장치

- 바이낸스 주문 번호는 자바스크립트 숫자 범위를 넘을 수 있어 확장은 항상 문자열로 다룬다.
- **부동소수를 쓰지 않는다.** `0.1 * 3 === 0.30000000000000004` 이라 부동소수로 내림하면
  경계에서 한 단위 틀리고, 그 수량은 `LOT_SIZE` 필터로 거부된다. 양자화는 전부 BigInt 정수
  연산이고, 문자열로 만든 뒤 다시 배수인지 확인한다.
- **즉시 체결을 막는다.** `bookTicker` 로 호가를 읽어, 롱 가격이 매도호가 이상이거나 숏 가격이
  매수호가 이하면 그 회차를 제외한다. 지정가를 쌓으려던 게 시장가가 되는 걸 방지한다.
- **포지션 모드를 조회한다.** 양방향(Hedge)이면 `positionSide` 를 명시하고, 단방향이면
  반대 포지션을 줄일 수 있다는 경고를 띄운다.
- **승인 대조.** 미리보기의 최종 양자화된 가격·수량·방향·포지션사이드를 해시해 두고, 실행할 때
  같은 조건으로 다시 계산해 대조한다. 다르면 전송하지 않고 새 표를 보여준다.
- **중복 주문을 막는다.** 응답이 유실되면 접수 여부를 알 수 없다. 그때는 재전송하지 않고
  `clientOrderId` 로 조회해 확정한 뒤 남은 회차만 보낸다.
- **실패를 두 종류로 나눈다.** 확정 거부는 다음 회차를 계속 보내고, 접수 불명은 즉시 멈춘다.
- **상태를 저장한다.** service worker 는 30초 유휴면 종료되므로, 회차 상태를 매 전송 전후로
  `storage.session` 에 기록한다.
- **증거금 검사.** `필요 증거금 = 실제 명목금액 합계 / 레버리지` 를 계산해 가용 잔고와 비교한다.
  비교 대상은 지갑 잔고가 아니라 `availableBalance` 다 — 이미 걸어 둔 주문과 포지션이 잡아 둔
  증거금이 빠진 값이라 그걸 써야 이중으로 세지 않는다. 모자라면 표 아래에 빨갛게 표시하고
  실행을 막는다. 미리보기와 **전송 직전에 각각 한 번씩** 재는데, 그 사이 다른 주문이 증거금을
  잡았을 수 있기 때문이다. 레버리지나 잔고를 못 읽었으면 검사하지 않는다 — 검사 못 한 것과
  부족한 것은 다르고, 못 읽었다고 정상 주문을 막으면 안 된다.
- **실행 잠금.** 분할주문·이어 보내기·전체 취소·Chase는 background service worker의 전역 단일 잠금을
  공유한다. 다른 작업이 진행 중이면 기다리지 않고 `BUSY`로 즉시 거부한다. service worker가 종료되면
  진행 중 작업과 메모리 잠금도 함께 사라진다.
- **키 없음을 화면에 드러낸다.** 키가 없으면 패널 위에 빨간 띠가 뜨고 실행 버튼이 잠긴다.
  눌러 봐야 아는 상태로 두지 않는다.
- **2단 확인.** 실행과 전체 취소는 한 번 더 눌러야 나간다. 브라우저 기본 대화상자
  (`confirm`)를 쓰지 않는 이유는, 크롬이 "이 페이지에서 추가 대화상자 차단"을 걸면 그 뒤로
  조용히 false 가 돌아와 버튼이 아무 일도 안 하기 때문이다. 돈이 나가는 경로에서 무음 고장은
  피한다.

## Chase 탭

`분할주문` 탭은 기존의 가격·금액 계산과 일괄 전송 화면이고, `Chase` 탭은 전체 심볼의 미체결
주문과 조건 감시 목록을 보여 준다. 현재 주소창 심볼의 `LIMIT` 주문 중 `NEW` 또는
`PARTIALLY_FILLED` 상태만 `[Chase]`와 `[조건]`을 사용할 수 있다. 다른 심볼은 목록 확인만
가능하고, 조건 감시를 켜는 일과 수동 Chase는 그 심볼 화면에서만 가능하다.

Chase는 `LIVE` 모드에서만 보낸다. `TEST`와 `PAPER`에서는 주문 수정 요청을 보내지 않고
`NOT_SENT`를 표시한다. 버튼은 두 번 눌러야 하며 확인창에는 주문 ID·심볼·방향·수량·감소전용
여부를 표시한다. 감소전용이 아니면 체결 시 포지션이 늘어날 수 있다는 경고를 함께 보인다.

### 조건 감시

주문 줄의 `[조건]`을 누르면 가격 조건과 선택 기준(`LAST` 또는 `MARK`)을 입력할 수 있다.
가격 조건의 방향은 켤 때 현재값과 목표값을 비교해 자동으로 정한다. 이미 목표에 닿았으면
켜지지 않고 `지금 Chase` 안내를 낸다. 청산 주문(`LONG+SELL`, `SHORT+BUY`, 단방향
`reduceOnly`)만 손익 조건을 추가할 수 있으며, 손익은 `LAST` 기준이고 수수료·펀딩은 제외한다.
가격 또는 손익 중 하나 이상을 넣어야 하며, `[켜기]`는 조건 요약을 먼저 보여 주고 두 번째
클릭에 `WATCH_ARM`을 보낸다. 같은 주문을 한 번 더 감시하지 않으며, 동시 감시는 심볼 10개,
주문 30개까지다.

감시 목록의 상태는 `대기`, `발동`, `추격 중(수정 횟수)`, `멈춤(사유)`, `해제(사유)`다.
체결 완료 항목은 알림 뒤 목록에서 자동 삭제한다. `PAUSED` 항목은 `[재개]` 또는 `[모두 재개]`를
누르면 주문·포지션·공백 중 도달 가능성을 항목별로 미리 보여 주고, 두 번째 클릭에서만 재개한다.
활성 감시는 `[해제]`와 `[전체 정지]`를 두 번 확인해야 한다. `[새로고침]`은 `WATCH_REFRESH`로
해제 항목도 정리한다.

감시 목록의 연결 상태는 `실시간`, `조회 감시`, `끊김`으로 표시한다. 웹소켓이 끊기면 REST 조회로
감시를 이어 가지만 조회 실패·대조 불완전·요청 한도 임박이면 감시를 멈추고 알림과 아이콘 배지를
표시한다. 절전, service worker 중단, 재시작으로 시계 공백이 생겨도 감시는 멈춘다. 공백 중 조건에
도달했을 가능성은 완성 1분봉으로 확인해 강조 알림만 내며 자동 Chase하지 않는다. service worker
재시작 뒤 자동 재개하지 않는다.

`notifications` 권한은 멈춤·해제·체결·공백 중 도달 가능성·재연결 실패를 Windows 알림으로
알리기 위해 필요하다. `alarms` 권한은 service worker가 유휴 상태여도 감시 시계와 공백 판정을
이어 가기 위해 필요하다. `action` 배지는 멈춤·해제 항목 수를 표시한다.

감시 목록 아래 `설정`에서 수정 최소 간격(ms), 분당 최대 수정 횟수, 조회 감시 간격(ms), 공백
기준(ms)을 바꿀 수 있다. 입력은 양의 정수이고 최소값은 각각 200, 1, 1000, 15000이다.
감시 상태·가격·체결 값은 디스크에 저장하지 않고 `storage.session`과 실행 중 메모리에서만 처리한다.

가격 입력칸의 `[현재가]`는 선택한 기준의 LAST 또는 MARK를 가져온다. `-1%`, `-0.5%`, `-0.1%`,
`+0.1%`, `+0.5%`, `+1%`는 현재 입력값에 적용하고 주문의 호가 자릿수로 반올림한다. 입력칸이
비어 있으면 먼저 현재가를 가져온다. 페이지 호가를 클릭하면 마지막으로 선택한 조건 가격칸에
채우며, 기존처럼 수량 접미사와 현재 호가에서 50% 이상 벗어난 값은 버린다.

수정 전 주문을 다시 조회해 화면의 스냅샷과 대조한다. 값이 바뀌면 `STALE`로 중단하고, 수정
응답의 주문 ID·수정 ID·가격·상태를 확인한다. 성공하면 `CHASED`와 이전 가격·새 가격·상태를
표시하고 수정 이력의 흔적도 별도로 표시한다. 바이낸스가 거부하면 `REJECTED`와 원문 메시지를,
요청 한도면 `RATE_LIMIT`을, 접수 여부를 확인하지 못하면 재전송하지 않고 `UNKNOWN`을 표시한다.
`UNKNOWN`이면 바이낸스 화면에서 직접 확인해야 한다.

수정 요청은 가격을 직접 넣지 않고 `priceMatch=QUEUE`로 보내므로, 공개 API가 이 조합을 실제로
받아들이는지는 소액의 실계정 지정가 주문으로 한 번 판정해야 한다. 성공하면 같은 주문 ID가
호가 줄 맨 뒤로 이동한다.

실계정 판정 절차는 다음과 같다.

1. 거래용 API 키를 쓰고 모드를 `LIVE`로 둔다.
2. 보유 포지션을 줄이는 최소 수량 지정가 주문 하나를 최우선 호가에서 멀리 건다.
3. 그 심볼 화면의 `Chase` 탭에서 `Chase`를 누른 뒤 `정말 Chase`를 한 번 누른다.
4. 다음을 모두 확인하면 성공이다.
   - `Chase 완료: 이전가 → 새 가격` 메시지가 나온다.
   - 새 가격이 그 순간 같은 쪽의 최우선 호가와 같다. 매도는 최저 매도호가, 매수는 최고 매수호가다.
   - 주문 상태가 `NEW` 또는 `PARTIALLY_FILLED`다.
   - 수정 이력이 `확인됨`으로 표시된다. 미확인이어도 수정 응답이 올바르면 Chase 자체는 성공으로 보되, 이력 표시는 보조 확인이다.
5. 바이낸스 거부 메시지(예: 가격 필수)가 나오면 공개 API가 가격 없는 수정을 받지 않는 것이다. 다시 누르지 말고 결과를 알린다.
6. `수정됐는지 확인하지 못했습니다`가 나오면 다시 누르지 말고 바이낸스 화면에서 주문 가격을 확인한다.

수정 이력 응답의 `amendment.modifyId` 중첩 구조는 [USDⓈ-M 주문 수정 이력 문서](https://developers.binance.com/docs/derivatives/usds-margined-futures/trade/rest-api/Get-Order-Modify-History)를 따른다.

## 일괄취소

`DELETE /fapi/v1/allOpenOrders` 한 번으로 **해당 심볼의 일반 미체결 주문 전부**를 취소한다.

바이낸스 화면에서 직접 건 주문도 함께 사라진다. 조건부(algo) 주문은 API 가 분리돼 있어
포함되지 않는다. 응답에 취소 건수가 없어서 전후 조회로 세며, 그 사이 체결이 있으면 숫자가
정확하지 않을 수 있다.
